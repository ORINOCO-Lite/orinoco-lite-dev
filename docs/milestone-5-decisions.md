## Accepted decisions

| ID | Outcome | Consequence |
| --- | --- | --- |
| M5-D001 | The Git metadata diff is the proposal and the candidate plan is ephemeral. | No tracked candidate inventory, duplicate review document, or retained source snapshot is required. |
| M5-D002 | Each adapter owns one compact current-state decision cache under `source-adapters/<adapter>/policy/curation-decisions.yaml`; Git stores its history. | The cache records accepted, rejected, and deferred claims without baseline/proposed records or an event graph. |
| M5-D003 | Git commits are the review transaction. DataLad records the proposal and programmatic metadata changes; a merge commit preserves the reviewed lineage. | Custom journals, transaction-recovery machinery, sidecars, reports, and attestations are prohibited. Linear-history-only downstreams are not supported. This supersedes M4-I008 for a conforming source-adapter consumer. |
| M5-D004 | The authenticated reviewer confirms the complete decision state. The hosted GitHub App posts on the user's behalf, the Action derives identity from the comment event, and the most recent triggering human is the Git author of a bot-applied change; automation is the committer. | The compact cache and Git/host history retain reviewer, time, source coordinate, and review URL without trusting browser-supplied identity or deciding who may approve production content. |
| M5-D005 | Git and DataLad record execution and review history; PAV records machine assertion provenance. | Additional W3C PROV is not activated without a demonstrated unanswered lineage query. |
| M5-D006 | No ontology-mapping representation is activated by Milestone 5. | SSSOM is used only if a genuine mapping set later requires it; rejection, identity linkage, and deduplication are not mappings. |
| M5-D007 | The shared canonicalizer, annotation-overlay join, candidate model, and finalizer are common Orinoco Lite behavior. The supported hosted review and compact-cache profile are GitHub-specific. Concrete adapters and policy remain site-owned. | No generic Python ABI, plugin framework, persistent adapter service, or second hosting-provider implementation is required. |
| M5-D008 | Canonical semantic metadata is stored in `metadata/records/` plus `metadata/overlays/annotations/` and joined before validation or RDF export. Records retain semantic assertion content; companions retain only PAV. | Human-facing record diffs remain readable while the resulting graph preserves upstream PAV semantics. Another overlay requires a focused specification change. |
| M5-D009 | The supported GitHub decision interface is a deployed web application backed by a minimal stateless GitHub App user-authorization service; the proposal commit contains the actual metadata diff, one expiring Actions artifact supplies presentation facts, and pull-request Markdown is an accessible fallback. | The service reads GitHub proposal and Actions objects and posts the complete proposal- and head-bound decision payload as the user; it runs no adapter or source logic, stores no metadata or curation state, and never commits, approves, merges, deploys, or writes to a source. GitHub Actions regenerates candidate facts and remains the trusted commit boundary. |
| M5-D010 | Annotation joining follows the pinned upstream distinction between object, data, and class-range assertions. Class-range URI assertions use the pinned `Statement` shape; non-string topical data retains its native type and uses a schema-typed lexical value in its `AttributeSpecification`. | The accepted shapes preserve assertion-level PAV without turning URI relationships into literals or coercing topical metadata to strings. |
| M5-D011 | The compact v1 cache contains only PID-keyed current decisions and the GitHub comment review blocks they reference. Reject and defer reverse candidate patches with Git three-way semantics; non-overlapping human edits survive and overlaps fail for correction. Accepted human corrections remove only untouched stale proposal PAV, empty companions are deleted, same-adapter rows are coalesced per PID, and candidate PID/path remain fixed during one review. | Git and GitHub retain history without an event ledger or whole-record restoration that could discard unrelated human work. The cache cannot ambiguously encode multiple independent same-adapter claims for one PID or silently retarget a reviewed claim. |
| M5-D012 | Canonical records store the same topical fields and qualified `AttributeSpecification` or `Statement` objects produced by the pinned enrichment helper. Companions select those stored objects and contain only their PAV; joins attach PAV and never derive qualified assertions from top-level scalars. Existing topical values survive source updates. When a topical field is absent but an equivalent human- or unowned qualified assertion exists, the adapter proposes the upstream convenience copy without claiming ownership or adding PAV. | This preserves the upstream assertion graph, subset matching, ownership coexistence, and human-priority behavior. Local code is limited to reversible compact/expanded PAV splitting and locked-schema typed normalization rather than a permanent scalar merge fork. |
| M5-D013 | Hosted review uses exactly one untracked, expiring, reproducible GitHub Actions presentation bundle containing source and proposal coordinates plus per-record UI facts. The proposal commit and metadata diff define candidate membership and operations; Git commits and the authenticated submission comment remain durable. | The GitHub App adds Actions read access, while the bundle remains neither a candidate authority nor persistent or recovery state. Pull-request Markdown has no machine protocol or native-diff cap, and the centrally published application origin remains configurable and self-hostable without creating a second host profile. |
| M5-D014 | SHACL Vue proposal editing is a distinct human-edit profile, not an input to the hosted decision-review bundle or finalizer. For every exact pull-request or current default-branch commit exposed for editing, trusted default-branch code publishes one expiring, reproducible artifact containing only `edit/config.json`, `edit/records.ttl`, and `edit/data/record-sources.json`. The central stateless application verifies the run and exact commit, combines those data files in browser memory with the generic shell and schema from an immutable released runtime, and exposes the normal version 2 bundle unchanged to the thin Orinoco wrapper. An explicit authenticated proposal writes one fixed-path temporary bundle-only handoff commit; trusted default-branch Python replaces only that exact commit with the equivalent attributed canonical metadata commit. | The editor-input artifact is presentation input, not metadata, a generated bundle, provenance, or durable curation state, and remains distinct from M5-D013's exactly-one decision-review artifact. The shared App uses metadata read, Actions read, contents write, and pull requests write; contents write is confined to same-repository human handoffs at exact coordinates after explicit public-data and no-secrets acknowledgment. The final branch retains no bundle, every earlier proposal/review commit survives, and SHACL Vue gains no GitHub, adapter, disposition, provenance, or cache semantics. No separate Worker, browser or hosted converter, database, object store, artifact cache, or persistent service is added. |
| M5-D015 | **Operational selection refined by M5-D021.** The original versioned identities for the Zotero and `dump-research-info` v1 adapters are `xyzri:XYZInstrument` records at `xyzrins:source-adapters/zotero/v1` and `xyzrins:source-adapters/dump-research-info/v1`. | Pinned upstream enrichment documentation and executable scrapers identify enrichers with versioned instrument records, and the pinned Things schema expressly includes software as an instrument. This row remains the historical v1 identity decision; it does not make v1 selectable for current runs. |

Remove those values upstream, preserve existing qualified `foaf:homepage` assertions, and represent the CON organization homepage with the same upstream `AttributeSpecification` pattern. | The adapter consumes corrected upstream Things without a local routing compatibility rule. Prefer exact PID, type, and label or name observed in the German public Things pool; use authoritative ROR identity for the ISSN International Centre, which that pool lacks; and reuse the existing JMLR venue Thing instead of modeling its website as a creator. | The downstream graph remains self-contained and schema-valid without unresolved network references, silently discarded fields, or copied provider graphs. This row is preserved as the historical policy behind source pull request 26 and downstream proposal 13; it is no longer the implementation direction. |
| M5-D018 | The hosted review application provides a bulk default that fills every currently unresolved candidate with `accept`, `reject`, or `defer`, preserves existing per-record choices, and leaves every choice editable before submission. | Bulk initialization is only transient browser state. The authenticated complete submission remains the first durable decision, and the trusted Action retains the same exact-head, completeness, regeneration, and authorization checks. |
| M5-D019 | Keep declared site-graph relationships locally closed, but apply upstream-style reference handling to `Identifier.creator`: validate it through the pinned `Thing`-range schema, resolve a matching local Thing when available, and otherwise preserve the external PID string without network access. Import controlled roles from their authoritative source root into the downstream's single record pool, union roots by PID, and reject unequal duplicates. Do not substitute a publication venue for a creator merely to close the graph. Omit JMLR's redundant generic `17-434` identifier because the canonical official article URL PID already retains that source key. | LinkML serializes the Thing reference as a PID string, and pinned qri preserves an unresolved PID scalar. | M5-D020 | The review application emits the complete authenticated `/curation submit` JSON inside one exact, closed-by-default Markdown `details` envelope while leaving the command as the visible first line. The trusted host also accepts the former exact unwrapped envelope for historical comments and event replays. | The long durable payload no longer dominates the pull-request conversation. This is a presentation-only transport change: payload format v1, reviewer authority, exact-head binding, completeness checks, and GitHub history remain unchanged. | M5-D021 | A curator selects a source adapter but does not supply its provenance identity. Trusted site configuration maps the current Zotero and `dump-research-info` providers to `xyzrins:source-adapters/zotero/v1` and `xyzrins:source-adapters/dump-research-info/v2`, respectively. The host derives the identity and requires an extant `xyzri:XYZInstrument` record whose adapter and version match the provider. | New proposals cannot fall back to an older identity or attribute current behavior to an arbitrary record. An incompatible provider change advances the provider version, reviewed identity record, and mapping together. Historical records remain provenance, not supported execution modes. Internal fields containing “agent” remain deterministic protocol bindings rather than operator choices or schema-class requirements. |

## Superseded exploration

The following are not dormant requirements and must not be restored without a focused specification change:

- tracked candidate inventories or full-record review bundles;
- append-only decision events or transaction graphs;
- `link`, `supersede`, permanent-exclusion, or conditional-deferral dispositions;
- custom reconciliation journals, locks, crash recovery, reports, or artifact attestations;
- squash- or rebase-compatible substitutes for preserving the original DataLad commit; and
- speculative template distribution, plugin APIs, or additional semantic overlays.

Implementation ambiguity is handled by stopping for clarification, not by adding another authority, artifact, or threat model.
